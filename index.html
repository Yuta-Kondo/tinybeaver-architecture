Fact Graph & Self-MoA

Two architecture decisions inside tinybeaver, my personal AI assistant: treating memory as a queryable knowledge graph instead of a growing chat transcript, and treating "think harder" as a governed parallel debate instead of one longer prompt.

FastAPI + SQLite + React Claude · GLM-5.2 · Gemini backend/memory_graph.py backend/main.py · generate_moa() Built with Claude Code

Most "AI with memory" demos append every message to one growing blob and re-summarize it when it gets too long. That degrades fast: facts contradict each other, nothing is queryable, and the context window fills with prose the model has to re-read every turn to find one sentence. tinybeaver stores memory as atomic, typed facts in a graph, retrieves them with hybrid search under a hard token budget, and — for questions worth more compute — runs a parallel multi-agent debate instead of a single completion. Below is how both actually work, with the honest gaps left in.

The whole project — backend, frontend, and this write-up — was built with Claude Code. That wasn't incidental to the project: I wanted to check whether an AI agent could help me build better agents. The memory design and the Self-MoA pipeline below are as much an answer to that question as they are features of the app.

01Why not just a bigger prompt

The first version of tinybeaver's memory was one markdown file per topic, rewritten wholesale after every turn. It worked until it didn't: topics overlapped (was a legal question admin or money?), files grew without bound, and there was no way to say "this fact replaced that one" — only "this file now reads differently." The fix wasn't a bigger context window; it was giving memory a schema.

02Memory as a fact graph

Every personal fact tinybeaver learns is stored as one row: a category, a text string, and links to the entities it involves. Facts don't get overwritten — a changed fact supersedes the old one, which is soft-deactivated and kept for history. Entities (people, orgs, places, projects) sit in their own table and connect through time-bound relations — an edge has a valid_from and gets a valid_to stamped shut when it's replaced, so the graph can represent "advised by X, then Y" without losing the first fact.

memory_facts(id, category, text, entity_ids, embedding, active, superseded_by, created_at)
entities(id, name, type ∈ {person,org,place,project,concept,other}, summary, updated_at)
relations(id, from_id, to_id, predicate, valid_from, valid_to)

Categories are a closed, MECE set of eleven life domains rather than an open tag field — closed so retrieval can reason about coverage, MECE so a fact has exactly one home instead of drifting across near-duplicate slugs. A resolver order breaks ties when a fact could plausibly fit two domains:

identity→ admin→ career→ money→ home→ body→ people→ craft→ play→ ops→ misc

adminGovernment, legal, and administrative paperwork
careerWork, research, jobs, professional life

Sitting above the eleven categories is one always-on core profile — a short synthesized paragraph capped at 3,500 characters, refreshed by the write path when identity-level facts change. It's the only thing injected on every single turn regardless of topic; everything else is retrieved on demand.

03How this differs from ChatGPT/Claude's built-in memory

Both ChatGPT and Claude.ai now ship a "Memory" feature of their own — the model saves facts about you across conversations there too, so the honest question is what a fact graph actually buys over that. I don't have visibility into either product's internals, so this is a product-level comparison based on what's visible as a user, not a claim about their code:

  • Flat list vs. structured store. What you can see and edit in ChatGPT's or Claude's memory panel is a short list of free-text bullets. tinybeaver's facts carry a category, links to typed entities, and time-bound relations — the equivalent of asking "everything currently true about my immigration status" and getting a filtered, deduplicated answer, with a visible reason each fact was retrieved (FTS match, semantic match, or both).
  • General-purpose vs. single-user-tuned. A consumer memory feature has to work reasonably for hundreds of millions of unrelated people through one shared mechanism, which is presumably why it stays conservative in size and opaque about retrieval — it can't be hand-tuned per user. tinybeaver only ever serves one person, so every number in the pipeline — eleven category domains, a 7,500-character budget, a 0.88 dedup threshold, the RRF weights — is tuned to one specific life, and I can see and change all of it.
  • Mine, not a product feature. If a vendor changes or retires their memory feature, whatever it stored goes with the product. This is a SQLite file on infrastructure I control — I own the schema and the retention rule (supersede, never overwrite) instead of inheriting whatever policy ships next.

I genuinely can't say with confidence whether ChatGPT's or Claude's memory is more or less size-constrained than mine under the hood. What I can say is that mine is inspectable end-to-end and built around one person's actual life domains, rather than a general mechanism that has to generalize across everyone's.

04Read path: hybrid retrieval under a budget

A cheap classifier call reads the incoming message and returns up to four relevant categories — never inventing new ones, since the catalog is closed. Retrieval then runs two searches in parallel against the fact table: SQLite FTS5 keyword search (BM25-ranked) and cosine similarity over Gemini embeddings, kept above a 0.28 similarity floor. The two ranked lists are merged with reciprocal rank fusion rather than either running alone:

score[fact] += weight / (60 + rank)   ·  weight = 1.0 for FTS, 1.2 for semantic

Fusing this way means a fact worded very differently from the query (which FTS misses) and a fact that's a rare exact term match (which embeddings can miss) both have a path to the top-24. Matched facts pull in their linked entities, and one hop of the relation graph around those entities gets appended too — so asking about a person surfaces not just facts about them but what they're connected to.

All of it is assembled against a hard 7,500-character context budget, trimmed greedily line-by-line so nothing gets cut mid-sentence — the model gets a bounded, structured memory block every turn, not an ever-growing one.

05Write path: extraction, not transcription

After each reply, a second Haiku call — not the main model, to keep it cheap — reads the turn and returns strict JSON: zero or more atomic facts, any new entities they mention, relations between entities, and an optional patch to the core profile. It's told explicitly to emit one fact per item, no essays, no general knowledge — the extraction target is a database row, not a summary.

Two safeguards keep the graph from just growing forever. Before a new fact is inserted, its embedding is compared against active facts in the same category; anything ≥0.88 cosine similarity is deactivated as a near-duplicate. And each category is capped at 80 active facts, oldest first to go. A separate "reflect" pass can be run on demand — an LLM reviews the whole active fact list at once and proposes merges or deactivations that per-turn writes wouldn't catch, since no single turn sees the full graph.

Why supersede instead of overwrite? A money fact from March and a contradicting one from August are both real — the second didn't erase the first, it replaced it at a point in time. Soft-deleting with a superseded_by pointer keeps that history queryable instead of just betting the newest write is always right.

06Self-MoA: debate instead of a longer prompt

The memory system answers "what does the model know." Self-MoA is a separate answer to "how hard should it think" — for questions worth the extra latency and cost, tinybeaver runs three parallel proposers on GLM-5.2 and has a fourth call synthesize them, rather than asking one model to be advocate, critic, and planner in a single pass.

The design follows Rethinking Mixture-of-Agents (2025): mixing several different vendor models as proposers tends to lower average proposal quality faster than the vendor variety helps, so all three proposers here are the same strong model. Diversity comes from three genuinely distinct system prompts and three different temperatures, not a shared prompt with a role label stapled on:

Advocate
glm-5.2 · temp 0.7
"Independently give your best recommendation… cover context and tradeoffs, then state a clear top recommendation."
Confidence: 0.82
Skeptic
glm-5.2 · temp 1.0
"Stress-test the decision space… argue for a different approach if the obvious recommendation looks flawed."
Confidence: 0.55
Operator
glm-5.2 · temp 0.6
"Plan under real constraints: time, money, energy… push back on over-planning. End with a concrete next step."
Confidence: 0.74

Every proposer is explicitly told it writes blind, in parallel, with no visibility into the other two — and closes with a forced Confidence: 0.XX line. That confidence isn't decorative: per Demystifying Multi-Agent Debate, vanilla debate between agents that just see each other's answers often fails to beat a simple majority vote — the gain comes specifically from diverse initialization plus confidence-weighted aggregation, not from debate rounds. So there's no back-and-forth here: three drafts once, then one synthesis call — closer to the parallel "all-agents-draft-then-decide" pattern than a sequential courtroom debate.

<agent name="Advocate" confidence="0.82">...</agent>
<agent name="Skeptic"  confidence="0.55">...</agent>
<agent name="Operator" confidence="0.74">...</agent>

→ synthesizer instruction: weight agreement by confidence, keep the
   strongest recommendation, honor valid critiques, include one concrete
   next step, surface dissent explicitly rather than averaging it away.

How it streams

All three proposers run on a thread pool and push into one thread-safe queue, so the discussion cards animate concurrently in the UI instead of appearing one after another:

start→ moa_brainstorm→ moa_agent_start moa_draft_delta moa_agent_done → moa_synthesizing→ delta …→ done

07What's still rough

  • no router

    Self-MoA is a manual toggle, not the complexity-gated auto-trigger the design memo scoped.

    Deciding "this question deserves 4 LLM calls instead of 1" well enough to trust automatically is an unsolved part of the design, not a shipped feature — it's an open question in my own notes, not a gap I noticed after the fact.

  • no timeout

    A hung GLM stream on one proposer thread can stall its queue slot indefinitely.

    Per-proposer failures are caught and isolated, but a slow response isn't an error — nothing currently bounds how long a "parallel" call is allowed to take.

  • silent aging

    The 80-fact-per-category cap trims oldest-first with no archive.

    Fine for a rolling personal-context window; not fine if a two-year-old fact quietly becomes unretrievable and nothing tells you it happened.
